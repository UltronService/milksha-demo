白話說明：門市裡誰跟誰講話？

顧客看大螢幕等取餐號。規格規劃是：店裡 POS 把「現在要顯示哪些號碼」送給奧創；奧創貼到電視上，再跟 POS 說「貼好了」或「電視沒連上」。

  • 門市 POS規格叫「既有送端」（達鈦）。
  • 奧創規格叫「接收端」：接收服務＋機上盒＋畫面。

規格沒寫掃杯貼、也沒寫機上盒去改 POS 裡的訂單。那是下面「想要的做法」多出來的一條路。

1. 文件目的與角色

本文件提供叫號機顯示廠商進行接收端串接。

  • 發送端（既有送端）：已在線上運行，依既有格式推送資料。會議確認：即門市 POS。
  • 接收端（我們）需完成：
    1. 接收叫號資料；
    2. 將資料顯示於指定門市螢幕；
    3. 回傳處理結果。

Request 與 Response 的欄位名稱、資料型別及結構不可任意修改。

2. 流程圖

2.1 迷客夏原規劃（規格有寫的）

POS 像櫃台把整份名單念一遍；奧創把名單貼上佈告欄，再跟櫃台說貼好了或佈告欄沒電。每次送來的是這家店此刻要顯示的完整名單。奧創回的是「有沒有顯示成功」，不是去改 POS 裡那張訂單。

迷客夏 Tammy 2026-09-24～29：上線前達鈦 POS 打迷客夏 URL；試點改打奧創接收端 URL，格式同規格。結帳送準備中、完成／掃碼後送可取餐，皆由 POS 外送。

2.2 想要的做法：POS、迷客夏 API 少改，機上盒能改 POS 訂單

差別：原規劃只有「顯示路」。你們要再加「寫回路」——店員掃杯貼後，機上盒去動 POS 裡那張單（例如改成可取餐）。顯示路可沿用規格 API；寫回路這份文件完全沒寫（圖上紅色虛線）。

少改與寫回會打架的原因：要改 POS 的單，POS 必須收得到機上盒的消息。若達鈦、迷客夏程式幾乎不動，只能借用他們現在已經在用的入口。規格沒保證有這扇門，所以要問達鈦／迷客夏；不能自己發明欄位。

迷客夏原規劃 你們想要的
誰送叫號畫面資料 POS 送給奧創 一樣（沿用同一套送法）
奧創回什麼 只回顯示成不成功 這段可留；另外還要能改訂單
掃杯貼 規格沒寫 機上盒掃完要寫回 POS
POS／迷客夏改動 POS 當送端（規格假設已上線） 希望少改 → 寫回要借用現有通道，否則 POS 仍要開一小扇門收人

欄位說明

欄位型別說明
merchant_idString商戶代碼
accountString帳號
isOKBooleanAPI 是否正常完成處理
informationString實際處理結果，內容為 JSON 字串

內層 JSON 字串解析

information 與 CallingNumberMasterResponse.result 為 JSON 字串，例：

"{\"isSuccess\":false,\"information\":\"目標叫號機尚未連線\"}"

解析後：

{
  "isSuccess": false,
  "information": "目標叫號機尚未連線"
}
欄位型別說明
isSuccessBoolean是否成功顯示至叫號機
informationString成功或失敗訊息

isOK = true 只代表 API 正常完成處理；實際是否成功顯示，需看內層的 isSuccess。

成功

奧創接收端架構草案（供迷客夏討論確認）

草案・待迷客夏確認

以下為奧創側試點接收端之工程方向摘要，供迷客夏 IT 與達鈦對接前對齊；細節以會議確認為準。本節標示草案者尚未定案。

架構概覽

達鈦 POS 以 HTTPS 呼叫奧創接收端 API（規劃部署於 Firebase Cloud Functions 第二代，區域 asia-east1）。接收端依規格檢查 payload 格式與簽章（方式待迷客夏確認）後，以 target 為鍵將該門市螢幕應顯示之整份名單寫入 Firestore；再依規格回傳 Response（外層 isOK、內層 isSuccess）。門市叫號螢幕／機上盒以即時監聽方式讀取 Firestore，更新準備中與可取餐區塊。

開發環境與正式環境（草案）

  • 規劃使用兩個獨立的 Firebase 專案：dev（內部與 Tammy 試送、奧創自測）與 prod（驗收通過後僅提供達鈦 POS 使用）。
  • dev 接收端 URL：https://<dev網址>/… 待提供 — 供迷客夏 Tammy 試送與奧創開發階段自測。
  • prod 接收端 URL：https://<prod網址>/… 待提供 — 驗收完成後交付達鈦設定；達鈦僅更換 endpoint URL，Request JSON 格式不變。
  • 切換上線：POS 端只改 URL，payload 與欄位名稱維持現行規格。

Firestore 狀態設計（草案）

以規格之 target 對應一筆門市螢幕狀態；路徑範例 stores/{target}（集合／路徑命名草案，可於會議調整）。

newsTicker選填；若 POS 有送則可存，螢幕端可選用或忽略（與 Q10 等待確認項目連動）

接收端處理規則（草案）

  1. 整批覆寫：同一 target 每次 Request 以本次 CallingNumberMasterRequest 內之清單，覆寫該 target 的準備中／可取餐陣列（與規格「送完整名單」一致）。
  2. 空陣列清空：某類別無資料時以空陣列表示，螢幕應清空該區塊（對應驗收項目 5）。
