> 範圍：展示用 Demo，只用假資料，不連接真實系統；不做跑馬燈（業主已決定）。
> 執行環境：Ultron Android APK 內的 STB（機上盒）網頁畫面。

### 1.2 直式 1080×1920

- **可取餐＝主角**：面積較大、字最大、黑底白字（對比 > 15:1）、每張號碼卡片有框。
- **準備中＝配角**：面積較小、字約為可取餐的一半、淺灰底中灰字（約 4.6:1），不搶眼。
- 每區標題列右側顯示頁碼（例如「1/2」），只有超過一頁時才出現。

## 2. 來源標籤

每個號碼旁（可取餐區在號碼上方；準備中區在號碼左側）放一個小標籤：**圖示字 + 文字**。
永遠有文字，不只靠顏色，色弱者也能分辨。顏色取自色弱友善色盤（Okabe-Ito）。

| 來源 | 規格 source_type 前綴 | 標籤文字 | 圖示字 | 底色 | 字色 | 備註 |
|---|---|---|---|---|---|---|
| 門市現場 | `From_Store_` | 現場 | 店 | #F2F2F2（淺灰白）+ 黑框 | #111 | 唯一「空心/淺色」標籤，形狀上也有差別 |
| 迷點（迷客夏 App） | `From_milksha_point_` | 迷點 | 迷 | #009E73（藍綠） | #000 | |
| foodpanda | `From_FoodPanda_` | 熊貓 | 熊 | #CC79A7（粉紫） | #000 | 若業主偏好可改「foodpanda」全名（較長） |
| Uber Eats | `From_UberEat_` | Uber | U | #0072B2（深藍） | #FFF | |
| UDD | `From_Udd_` | UDD | D | #E69F00（橘黃） | #000 | |

標籤字高：可取餐區約 30–34px、準備中區約 24–26px。

## 3. 號碼變成「可取餐」：彈出放大 + 提示音（全螢幕 overlay + ding-dong）

- **畫面**：整個畫面蓋上半透明深色遮罩（純色透明，不用模糊），中央白底大卡片顯示：來源標籤、超大號碼（橫式約 320px 字級、直式約 300px 且寬度不超過螢幕 85%）、「請取餐」。
- **時間：每筆約 2.8 秒**
  - 0 – 0.3 秒：放大淡入（由 60% 放大到 100%），同時播放「叮咚」提示音
  - 0.3 – 2.5 秒：停留
  - 2.5 – 2.8 秒：縮小淡出，號碼落回可取餐區第一格
- **落地後**：該號碼卡片加粗白框約 10 秒（靜態，不閃爍），讓顧客看出是剛叫到的。
- **同一次推送有多筆新的可取餐**：排隊一筆一筆播放，**最多播 3 筆**；第 4 筆起不彈出、不響，直接加入列表（仍有粗白框）。
- **播放中又收到新推送**：新的可取餐號碼接在隊伍後面，待播總數仍以 3 筆為上限；若某筆還沒輪到就已經被取走（從資料消失），直接跳過。
- **號碼被取走（從資料中消失）**：直接移除，不做動畫，其他號碼往前補位。
- **開機／重新整理後的第一份資料**：只顯示，不彈出、不響（避免一開機連響十幾聲）。

## 4. 如何判斷「哪一筆剛變成可取餐」（比對前後兩份完整名單）

迷客夏每次都送「目前完整名單」，不是只送變動。看板自己比對：

1. 每筆號碼用「來源 + 號碼」當身分（例：`現場-1523`）。來源由 source_type 去掉 `_OK` / `_Preparing` 取得。
2. 這次名單中是可取餐（`_OK`）、但**上一次名單的可取餐裡沒有它** → 算「新叫到」→ 進入彈出隊伍。
   （不論上一次它是在準備中、還是直接第一次出現就是可取餐，都會彈出。）
3. 上一次有、這次名單完全沒有 → 算「已取走」→ 直接移除。
4. 同一號碼同時出現在準備中與可取餐（資料異常）→ 只顯示在可取餐。
5. 收到空陣列 `number_content: []` → 清空兩區（規格第 8 節明訂）。
6. 看板在本機記錄每筆「第一次出現在該區的時間」，用來排序（因為規格裡沒有訂單時間欄位）。

## 5. 排序與分頁（號碼很多時）

- **可取餐區**：最新叫到的排最前面（左上 → 右 → 下一列）。
- **準備中區**：等最久的排最前面（以第一次出現的時間；同一批同時出現的依資料陣列順序）。
  - 備案：若業主較習慣依號碼大小排列，可切換為號碼由小到大（注意號碼是字串，例如 "0871"，要以文字方式比較並保留前導 0）。
- **每頁筆數（沿用既有規則）**
  - 每頁列數 = max(3, floor(可用高度 ÷ 列高))
  - 每頁筆數 = 每頁列數 × 欄數
- **每區上限（每頁最多格數）**：橫式 可取餐 3×4=12、準備中 2×9=18；直式 可取餐 2×4=8、準備中 3×5=15。
- **自動換頁**：頁數 > 1 才輪播，預設每 6 秒換一頁；標題列顯示「1/3」，底部細進度條。
- **有新的可取餐號碼時**：可取餐區跳回第 1 頁並重新計時（準備中區不受影響）。
- 兩區各自獨立換頁；門市端不捲動、不需要觸控。

## 6. 遠距可讀性

| 項目 | 橫式 | 直式 |
|---|---|---|
| 可取餐號碼字級 / 數字實高 | 140px / 約 100px（螢幕高 9%） | 180px / 約 130px（螢幕高 6.8%） |
| 準備中號碼字級 / 數字實高 | 64px / 約 46px（4.3%） | 80px / 約 58px（3%） |
| 彈出大號碼 | 約 320px | 約 300px |

- 最低原則：可取餐數字實高 ≥ 螢幕高 6%；準備中 ≥ 3%。粗略換算：數字高 10cm 約可在 30m 內辨識。
- 對比：可取餐 #161616 底 / #FFFFFF 字；準備中 #E4E4E4 底 / #6A6A6A 字。
- 字型：Noto Sans TC（思源黑體）Black/Bold，數字使用**等寬數字**（CSS `font-variant-numeric: tabular-nums`），號碼更新時不會左右跳動；備選 Roboto Mono。字型需打包在 APK/本機，不依賴網路字型。
- 號碼以字串顯示，保留前導 0（"0871" 不可變成 871）。

## 7. STB 效能注意事項

- 動畫只用 `transform`（縮放/位移）與 `opacity`（透明度）；不用模糊、陰影、漸層動畫、影片、GIF。
- 同一時間最多 2 個動畫在跑（彈出卡片 + 頁碼進度條）。換頁用直接切換或 0.3 秒淡入淡出。
- 每次推送整批重畫一次清單即可（名單最多數十筆），不要每筆各自計時器。
- 提示音用一個短音檔（< 1 秒、預先載入）；需確認 APK WebView 允許自動播放聲音。
- 長時間開機：避免記憶體累積（舊號碼資料要清掉、計時器要重用）。

## 8. 展示控制（Demo 用）

- **看板網址保持乾淨**：一般網址不出現任何按鈕。
- **A 方案（建議，STB 適用）**：網址加 `?demo=1` 才啟用。右下角一個小把手「⚙ 展示」，點擊或按 **D 鍵／遙控器選單鍵** 打開右側抽屜面板；閒置 10 秒自動收起。
- **B 方案（筆電接大螢幕時）**：另開 `/control` 控制頁當遙控器（同瀏覽器頁面間傳送），看板頁完全不顯示控制元件。
- **面板功能**
  - 「▶ 模擬推送（下一步）」：送出劇本中的下一份完整名單（格式與正式資料相同）。
  - 自動播放：開/關；間隔 5 / 8 / 10 秒（預設 8 秒）；播完自動循環。
  - 劇本選擇：一般時段（12 步）、尖峰爆單（一次 5 筆可取餐，測試「最多彈 3 筆」）、跨頁測試（約 40 筆，測試換頁）、清空測試（空陣列）。
  - 手動加號：選來源、輸入號碼、選狀態 → 加入並推送；隨機一筆改可取餐；隨機取走一筆。
  - 清空畫面、重置劇本、提示音開關、橫/直版面切換。
  - 顯示最近一次推送的假資料（`number_content` 摘要）。
  - 快捷鍵：D＝開關面板、空白鍵＝模擬推送、A＝自動播放。
- **一般時段劇本示意**：1 開機 6 筆準備中 → 2 新增 2 筆準備中 → 3 一筆轉可取餐（彈出）→ 4 兩筆轉可取餐（依序彈出）→ 5 一筆被取走（直接消失）→ … → 12 清空後重來。

## 9. 規格書（PDF）中本頁會用到的欄位

來源：《叫號機接收端 API 串接規格》（8 頁）。

| 欄位 | 型別 | 本頁用途 |
|---|---|---|
| `serviceSpecialData_Json.data.number_content` | 陣列 | 門市目前完整叫號名單（每次全量） |
| `number_content[].source_type` | 字串 | 來源＋狀態，10 種固定值（見下），需「整個字串完全比對」 |
| `number_content[].number` | 字串 | 顯示號碼；**必須當字串處理，不可轉成整數** |
| `serviceSpecialData_Json.target` | 字串 | 目標叫號機識別（例：`composec030020`），決定顯示在哪個門市螢幕；Demo 中僅示意 |
| `merchant_id` / `account` | 字串 | 品牌代碼 / 門市帳號；Demo 不顯示，僅保留於假資料 |
| `timeStmp` | 字串 | 資料產生時間（例：`2026-07-17-13-17-00:2831`）；可用於判斷推送先後（見待確認） |

source_type 全部 10 種：
`From_Store_Preparing / From_Store_OK`（門市現場）、
`From_milksha_point_Preparing / From_milksha_point_OK`（迷點）、
`From_FoodPanda_Preparing / From_FoodPanda_OK`（foodpanda）、
`From_UberEat_Preparing / From_UberEat_OK`（Uber Eats）、
`From_Udd_Preparing / From_Udd_OK`（UDD）。
結尾 `_Preparing` → 準備中區；`_OK` → 可取餐區。

本頁**不使用**的欄位：`newsTicker_content`、`newsTickerSpeed`（跑馬燈，業主決定不做）、`isEncrypt`、`serviceSpecialData_Json_Md5Hash`、`signature`，以及整個 Response（`isOK`、`information`、`reslut`、`resultMd5`、`reesultMd5_ServerSignature`、`isEncrypted`）——這些屬於正式串接，Demo 不處理。
注意：規格明言 `timeStmp`、`reslut`、`reesultMd5_ServerSignature` 拼字特殊但不可更改，日後正式串接照抄。

## 10. 待確認問題（從 PDF 發現）

1. **跑馬燈 vs. 驗收項目**：業主決定不做跑馬燈，但 PDF 第 13 節驗收項目第 6 條是「跑馬燈內容及速度更新」。正式上線時是否免測此項，需與迷客夏確認。
2. **範例品牌不一致**：Request 範例是 `merchant_id: "compose"`、`target: "composec030020"`、「COMPOSE 臺北信陽店」；Response 範例卻是 `"Milksha"` / `"Tammy001"`。迷客夏實際的 merchant_id / account / target 格式為何？
3. **沒有訂單時間**：每筆號碼只有 source_type 和 number，沒有下單/完成時間。「最新在前 / 最久在前」只能靠看板自己記錄第一次看到的時間；陣列本身的順序是否有意義（例如已按時間排序）？
4. **沒有門市名稱欄位**：若要在頁首顯示門市名，只能從 target/account 對照，或另行設定。
5. **號碼格式**：範例都是 4 位數（"1488"、"1985"）。最長幾位？會不會有英文字母或前導 0？不同來源會不會用同一個號碼（例如現場 1523 與 Uber 1523 同時存在）？本設計以「來源＋號碼」區分。
6. **推送頻率與順序**：多久推一次？若網路延遲導致舊資料晚到，是否以 `timeStmp` 丟棄較舊的資料？`timeStmp` 冒號後的數字（`:2831`）代表什麼？
7. **未知的 source_type**：規格要求「依完整字串判斷」，若收到不在 10 種內的值（例如大小寫不同），要忽略還是顯示為「其他」？
8. **同號碼同時在兩個狀態**：理論上不應發生，本設計以「可取餐優先」處理，需確認。
9. **`newsTicker_content` 為空陣列時清空跑馬燈**：因不做跑馬燈，本頁忽略；確認迷客夏不會依賴跑馬燈傳遞重要公告（例如「暫停外送」）。
10. `isEncrypt = true` 時的解密方式 PDF 未說明（Demo 不影響，正式串接需要）。
