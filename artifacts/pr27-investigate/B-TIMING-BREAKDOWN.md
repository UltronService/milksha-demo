## 總監補充（白話）

### 1. 「看板每 0.5～2 秒去拿一次號碼」和「有變化才通知」是不是同一件事？

**有關，但不是同一句話。**

- **現在（輪詢）**：看板像每隔一段時間去問雲端「號碼有沒有變？」——開板後前 20 秒約 **每 0.5 秒**問一次，之後約 **每 2 秒**問一次；另外還有讀裝置指令等。
- **省錢方案（有變化才通知）**：改成「雲端號碼一變，主動通知看板」，平常沒變就不用一直問。

所以：**都是在解決「看板怎麼知道號碼更新了」**；差別是 **一直問（輪詢）** vs **變了才告訴你（推播／監聽）**。後端估算裡把「每秒讀一次」改成「有變化才通知」，指的是 **減少這類重複讀取**，和看板目前 0.5s/2s 輪詢 **是同一類成本來源**，但 **實作方式不同**。

### 2. 能不能一次同時解決速度與費用（例如 Firestore 即時監聽）？

**可以朝這個方向做，但要換做法，不是把輪詢再加快。**

| 項目 | 說明 |
|------|------|
| **按下→出號（預估）** | 就緒後：若改為監聽 `today_board`，多數情況可壓到 **約 1 秒內**（zz-qa 實測暖送已 ~0.4s）；**首輪冷啟動**仍可能 **1–2 秒+**，需另做後端保溫或預熱。 |
| **500 店月費（僅引用後端估算）** | 後端文件：**約 NT$49,000/月** → 調整後 **約 NT$13,000–14,500/月**（省在減少無效讀取／通知化）；**本 repo 無細項拆分，不另編數字**。 |
| **誰要改** | **看板前端**（讀取方式：REST 輪詢 → SDK 監聽或等價推播）、**Firestore 規則與後端寫入**（確保店別隔離、token 只能讀自己店）。 |
| **風險** | 舊 Android／舊 WebView 要驗 SDK；**斷線重連**要補「重連後全量對齊 seq」；規則錯會 **漏號或跨店**；監聽連線數在 Firebase 計費模型下要與後端一起算。 |

**輪詢加快（例如永遠 0.5s）通常只會更快一點，但讀取次數大增，與省錢目標相反。** 要 **又快又省**，應是 **監聽 + 停掉或大幅放慢無效輪詢**，不是兩套並行加倍讀。

### 3. 費用數字來源

僅引用負責人提供之 **milksha-cloud 後端估算**（500 店 **~NT$49,000/月** → 優化後 **~NT$13,000–14,500/月**）。本機未 clone milksha-cloud 細表時，不補充未證實拆分。
