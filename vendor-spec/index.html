Ultron 機上盒 APK 修改規格 v0.3（迷客夏・新方案）

對象：外包 Android 廠商 · 基準：v0.2 改版 · 定案日：2026-10-02 · App：com.ultron.player

文件索引： API 討論規格 · 迷客夏簽認確認書 · 要問達鈦的問題

0. 新方案白話摘要（2026-10-02 定案）

試點改為：POS 在店內用一般 HTTP（不加密）把「整份叫號名單」送到該店叫號機上盒；上盒存好本機後依迷客夏格式回覆 POS，並把名單整份交給看板網頁；上盒再用加密連線上傳雲端（雲端細節由奧創後端負責，不在本頁展開）。

  • 一店一螢幕、一上盒；路由器固定 IP 尾碼 .223（例：10.3.X.223）。
  • 新店內 API：2757 埠（可設定）；舊 2756 聯發逐筆格式保留不動，以免影響其他客戶。
  • 營業日結束：台灣時間 03:00 全門市清空（v0.2 若寫 04:00 以本版為準）。
  • 不做歷史區；號碼何時從畫面移除等規則待負責人決定，實作須可調整。

1. 背景與範圍（相對 v0.2）

迷客夏松山試點：POS 送整份名單＋杯貼掃描叫號（選項 B）仍成立。v0.3 新增 HTTP 接收（2757）、迷客夏 Request／Response 回覆、本機持久化與雲端補傳；關閉轉送 .220–.230 其他上盒。

廠商負責：常駐背景服務、HTTP 接收與健康檢查、本機儲存、回 POS、整份名單交網頁、掃描槍、2756 舊埠相容、修 CPU 空轉、Release 安全清理、設定項。

不在範圍：叫號網頁版面／音效（奧創前端）；達鈦 POS 程式；路由器設定；雲端後台程式（奧創後端，但上盒須依接口上傳）。

2. 現況（v186，摘要）

項目現在怎樣主要問題
接收方式TCP 2756，一次一張單 JSON，無回覆與迷客夏「整份名單＋簽章＋回覆」不同
生命週期在 MainActivity 裡開 Server，非前景服務易被系統回收；開機不穩
讀取用「有沒有資料可讀」空轉輪詢每條連線可能吃滿一顆 CPU
轉送收到後轉送同網段 .220–.230迷客夏一店一上盒，應關閉
網頁逐筆呼叫看板，非整份名單新方案要「一有變動就整份交給網頁」
斷電畫面狀態不保留新方案要求本機持久化、重開合併
正式版10053／v186 曾指向測試網域；除錯上傳 Firestore須一併修正（見第 8 節）

3. 修改項目（現況 → 目標 → 驗收）

3.1 店內 HTTP 接收（2757）

現況要改成怎樣怎麼驗收
僅 TCP 2756 逐筆新增可設定的 2757；接受 POST 整份名單（迷客夏 Request 包裝）；提供 GET 健康檢查供達鈦與現場確認上盒在線用測試工具對 10.3.X.223:2757 送整份名單，收到符合規格的 Response；GET 健康檢查回成功；2756 舊客戶連線仍可用
店內無 TLS店內 HTTP 明文；上傳雲端才 HTTPS（上傳模組由奧創提供接口規格）抓包確認店內為 HTTP；雲端連線為加密（與後端聯測）

3.2 回覆 POS 與本機儲存

現況要改成怎樣怎麼驗收
不回覆 POS依《叫號機接收端 API 串接規格》回覆（含 isOK、information、內層 isSuccess 等拼字不可改）比對 Response 欄位與範例；成功／格式錯誤／儲存失敗等情境各測一次
無本機佇列每筆先寫入本機儲存，存成功才回成功；存失敗回失敗讓 POS 重送；斷電重開不可丟送名單後立刻斷電重開，資料仍在；模擬寫入失敗時 POS 收到失敗
—待確認 規格裡「目標叫號機尚未連線」等訊息，在新方案（POS 直連上盒）下語意需與迷客夏對齊後調整回覆文案定案後更新測試案例

3.3 簽章與防冒送

現況要改成怎樣怎麼驗收
無驗簽店內先不擋單；POS 簽章原樣隨上傳雲端，雲端只紀錄驗簽結果送錯簽名仍可在店內顯示；雲端後台可查到驗簽失敗紀錄（與後端聯測）
—驗簽金鑰不得寫進 App反編譯／設定檔檢查無金鑰明文

3.4 斷網、重開、狀態合併

現況要改成怎樣怎麼驗收
斷外網畫面可能空白外網斷時畫面照常顯示；資料排隊存上盒，恢復後依流水號補傳；狀態只往前走，舊資料不可蓋掉新狀態拔外網線操作 30 分鐘，客人畫面仍有號碼；恢復後雲端與本機一致且無狀態倒退
重開空白重開先顯示本機上次名單，再與雲端同步合併（只往前走）；過程不顯示「更新中」；若仍斷網就顯示上次號碼重開前後錄影；無「更新中」字樣；合併後號碼正確
重連可能補響重連或整份重送不補響、不補語音；只有新出現的可取餐才響重送整份名單後聲音次數不增加；新號碼可取餐才響

3.5 畫面與連線提示

現況要改成怎樣怎麼驗收
可能顯示連線問題客人看的畫面不得出現「連線中斷」類提示；上盒定時向雲端報平安，後台顯示離線與最後連線時間目視客人畫面；後台可見離線標記（與後端聯測）
04:00 或未統一全門市 03:00（台灣時間） 清空；接收紀錄保留 7 天 後自動刪調整測試時鐘或設定項驗證；紀錄第 8 天自動清除
可能有歷史區不做歷史區；可取餐何時移除等 待負責人決定（規格書：可取餐留到掃掉／空名單不清／準備中離開 60 秒等），須做成可設定定案後跑對應 QA 案例

3.6 常駐服務、CPU、網頁整份名單

現況要改成怎樣怎麼驗收
Activity 綁 Socket；CPU 空轉前景服務常駐、開機自啟；修掉每連線空轉占滿一核心；阻塞式讀取閒置 10 分鐘 CPU 平均 < 1%；force-stop 後 60 秒內恢復；dumpsys 顯示前景服務
逐筆 getOrderStatus名單任一變動即把整份交給看板網頁（接口由奧創前端與廠商對接，須低延遲）測試頁或正式網頁收到整份快照；POS 送全量後一次更新
轉送 .220–.230關閉迷客夏路徑下的轉送（2756 行為可保留給其他客戶但須可關）監聽同網段其他 IP，確認無轉送封包

3.7 掃描槍（沿用 v0.2，略述）

杯貼「取餐號,訂單類型」：掃一次→可取餐（要響）；再掃→移除。斷 POS 時掃描仍可用；細節與 v0.2 §3.4–3.6 相同，但合併規則須配合「整份名單＋只往前走」。

3.8 設定

  • HTTP 埠（預設 2757）、2756 開關、Store／target、營業日結束時間（預設 03:00）、是否啟用舊轉送等須可遠端或本機設定。
  • IP 尾碼應為 .223：非 .223 時可告警（維持 v0.2 橫幅邏輯），但不阻擋客人看板。

4. 驗收清單摘要（對齊 QA v0.2）

完整清單共 186 項，其中 107 項必過（P0）。新方案下約一半測項須改寫（例如 TCP 2756 逐筆、fullTicketStatus、ScanReport 回 POS 等），改寫前請以本 v0.3 為準。

必過重點（摘要）：
  • 服務與穩定：開機 60 秒內可收單；被殺後恢復；無 CPU 空轉；8 小時長測記憶體與 CPU 不超標（§6.5）。
  • HTTP 2757：整份名單 POST、健康檢查 GET、Response 格式與儲存後才成功。
  • 斷網／重開：外網斷畫面不空；重開不丟單；不補響；客人畫面無斷線字樣。
  • 掃描：焦點、連掃、非法碼、Back 不可關 App、2 小時不休眠等（G 系列 P0）。
  • 安全：Release 不可除錯、正式勿指向測試伺服器、勿把訂單原文上傳除錯 log（見第 8 節）。
  • 升級：簽章金鑰問題未解前為阻擋項（I-05／I-12）。
  • 營業日：03:00 清空（C 系列）；空名單／移除規則待 Q-46 定案後重測。

詳細案例編號見 QA 草稿「§3.1 規格書對照表」；HTTP 相關請新增／改寫對應編號並標 v0.3。

5. 待達鈦／迷客夏確認（影響實作）

  • POS 能否用「所在網段、尾碼改 223」自動算出上盒位址（500 店只設一次）。
  • 店內 HTTP 是否可接受；2757 與路徑能否全國統一設定。
  • 沒收到回覆是否重送、間隔與次數；上盒重開 1–2 分鐘送不到時行為；是否支援第二備援位址。

問題清單見 要問達鈦的問題。
